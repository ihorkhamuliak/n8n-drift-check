# n8n-drift-check

[English](README.md) · **Українська**

Щоденна перевірка однієї пастки n8n 2.x: **те, що видно в редакторі, не завжди те, що виконується.**

Редактор і будь-яка пряма правка SQL змінюють `workflow_entity`. Опублікований воркфлоу виконується з `workflow_history`,
з версії, на яку вказує `activeVersionId`. Коли вони розходяться, нічого не падає і ніхто не попереджає.

Мені це коштувало двох збоїв. Один раз зміна мови була в базі й у кожній моїй перевірці, а старий воркфлоу кілька днів постив далі.
Другий раз виправлення добу лежало у `workflow_entity` і не виконувалось.

## Що робить

Для кожного активного воркфлоу порівнює `nodes` і `connections` у двох таблицях як JSON, тож форматування не заважає.

| Код виходу | Значення |
|---|---|
| `0` | усе збігається |
| `1` | хоча б один воркфлоу розійшовся |
| `2` | сама перевірка не спрацювала |

Той самий набір розбіжностей повідомляється один раз. Новий набір одразу, і момент, коли він зник, теж.

## Чому їй можна вірити

Перевірка, яка завжди мовчить, нічого не доводить. На кожному запуску вона копіює активні воркфлоу в тимчасову таблицю,
садить розбіжність у всі й виконує той самий запит. Якщо хоч одну пропустила, повідомляє, що сліпа.
Таблиця зникає на `ROLLBACK`, справжні таблиці лише читаються.

## Налаштування

Python 3 і `docker` на хості з self-hosted n8n і Postgres. Залежностей нема.

```bash
python3 n8n_drift_check.py
```

| Змінна | За замовчуванням | Значення |
|---|---|---|
| `N8N_PG_CONTAINER` | `n8n-postgres-1` | контейнер Postgres |
| `N8N_PG_USER` | `n8n` | користувач бази |
| `N8N_PG_DB` | `n8n` | назва бази |
| `DRIFT_STATE` | `n8n-drift-state.json` | памʼятає, про що вже повідомлено |
| `DRIFT_ALERT_CMD` | порожньо | будь-яка команда shell, що читає тривогу зі stdin, наприклад відправник у Telegram |

Щоденний cron:

```cron
30 7 * * * cd ~/n8n-drift && DRIFT_ALERT_CMD='/usr/local/bin/notify' python3 n8n_drift_check.py >> drift.log 2>&1
```

## Межі

- Розбіжність не завжди помилка: неопублікована чернетка в редакторі теж її дає. Спершу гляньте, що саме розійшлось.
- Сам cron ніхто не стереже. Якщо він зупиниться, сигналу не буде.
- Назви таблиць і колонок з n8n 2.25 і 2.41. Новіша версія може їх змінити, тоді перевірка вийде з кодом `2`.
